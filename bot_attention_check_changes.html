Bot check (captcha) changed

Before: on a wrong answer, check_fn returned false, which made the plugin refuse to finish the trial — stuck on the page, and the wrong attempt was never saved anywhere (only a correct answer ever got recorded, and only the answer itself, no pass/fail flag).

const valid = window.validateCaptchaForm();
if (valid) {
  this.data.form_data = JSON.stringify(getFormData(this.data.form_id));
}
return valid;const correct = window.validateCaptchaForm();
this.data.form_data = JSON.stringify(getFormData(this.data.form_id));
this.data.captcha_correct = correct;
this.data.captcha_target_word = window._captchaWord;
return true;

Now: the trial always finishes. Three things get saved regardless of correctness — the typed answer (already existed, now saved even when wrong), a captcha_correct boolean, and captcha_target_word (the actual highlighted word for that session, so correctness is independently checkable later rather than trusting a stored boolean).

Now: always finishes, and both the actual typed text and an attrition_correct boolean are saved — this also fixes the pre-existing gap where the typed sentence wasn't being captured at all.

Does any of this actually stop AI, or is it easy to get past?

Honest answer: this stops careless/rushed humans and naive scripted bots. It would not meaningfully stop a deliberate AI-driven respondent. All three checks share the same weakness — the "secret" is always sitting in plain, unobfuscated text in the page itself:
  • Captcha word: set via document.getElementById("captcha-word").textContent (captcha.html) — anyone or anything reading the DOM (a real CAPTCHA solver, a scraping script, or an LLM given the page's text/HTML) gets the answer directly. There's no distortion, no image, no audio, none of the actual anti-bot mechanics a real CAPTCHA (reCAPTCHA/hCaptcha) uses.
  • Attrition sentence: the exact required sentence is printed right there on the page to be copied. Passing it proves the text was reproduced correctly, not that a human (vs. an automated agent) did it.
  • KAI "select Easy": this is a reading-comprehension instruction embedded in plain text — exactly the kind of task an LLM is very good at, not something that trips it up.
This class of check is a standard, well-established technique in survey methodology for catching inattentive or careless human respondents (someone speed-clicking through without reading), and it does filter out the most naive bots (fixed-response spam scripts that never look at page content at all). But an actual AI agent capable of reading a rendered page and typing a response would sail through all three without effort — none of them test anything an AI is bad at. If deliberately AI-driven fraudulent responses (rather than careless humans) are the specific threat you're worried about, the fix isn't a better instructed-response item — it's a different category of tool entirely: a real CAPTCHA service (reCAPTCHA v3 / hCaptcha, which score behavioral signals server-side), leaning on your survey platform's own bot/fraud screening (CloudResearch/Connect, which this study already runs on), or server-side signals like unusually fast completion + no mouse movement. Happy to help wire up any of those if that's the actual concern — just flagging that what's in place today answers a different question ("was this response careless?") than "was this a bot?"
